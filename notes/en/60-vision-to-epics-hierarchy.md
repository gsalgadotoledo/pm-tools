# 60 - From Vision to Epics: The PM Hierarchy

> New chapter: Building Products Day-to-Day

## The Hierarchy

```
Vision (CEO/Founders)
  └── Goals (Executives → defined as metrics)
       └── Initiatives (Management teams)
            └── Releases (grouped features shipped on a date)
                 └── Epics (grouping of features/functionality)
                      └── User Stories + Acceptance Criteria
```

## Example

| Level | Example |
|---|---|
| **Vision** | Become the #1 language learning platform globally |
| **Goal** | Increase new users by 5% this year |
| **Initiative** | Translate the product into 3 new languages |
| **Release** | February release: all 3 languages available |
| **Epic** | Translate app to Spanish |
| **User Story** | "As a user, I want to switch the app language to Spanish so I can use it in my native language" |

## What is an Epic?

- PM lingo for a **grouping of features/functionality** to build
- The fundamental brick PMs build with
- Teams typically build **3-5 epics per quarter**
- Takes **longer than one sprint** (if shorter → just a user story)
- NOT always user-facing (e.g., "migrate database" is an epic too)

## Epic Spec Sheet (Requirements Document)

| Section | Owner | Content |
|---|---|---|
| **Introduction** | PM | What, why, metrics to improve, MVP vs ideal state, supporting links |
| **Product Requirements** | PM | Detailed functionality needed (must be fast, must support X language, etc.) |
| **Design Requirements** | Designer + PM | Wireframes, prototypes, visual specs (resolution, sizing, UX decisions) |
| **Engineering Requirements** | Engineers | Database needs, API endpoints, scaling, tech dependencies |

> The spec sheet must be **accessible to anyone** in the company.
