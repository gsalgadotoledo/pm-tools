# 63 - Roadmapping

## The Uncomfortable Truth

Roadmaps are **almost always inaccurate** — and that's okay.

If you're doing Agile, you can't predict 3-4 months out. Problems shift, competitors change, experiments fail.

## Two Types of Roadmaps

### 1. Time-Based (Quarterly) Roadmap

```
Q1: Feature A, Feature B
Q2: Feature C, Initiative D
Q3: Feature E, Feature F
```

| Pros | Cons |
|---|---|
| Executives and investors like seeing dates | Inaccurate if you're being agile |
| Useful when real deadlines exist (B2B sales commitments) | Creates false expectations |
| Good as a **general guide** | Not meant to be taken literally |

**When it works**: B2B companies with sales-driven deadlines ("customer needs this by February").

### 2. Priority-Based (Now/Next/Later) Roadmap

```
| NOW (weeks)      | NEXT (months)    | LATER (someday)  |
|------------------|------------------|------------------|
| Epic A           | Epic D           | Epic G           |
| Epic B           | Epic E           | Epic H           |
| Epic C           | Epic F           |                  |
```

| Pros | Cons |
|---|---|
| No dates = no false expectations | Executives may push for dates |
| Agile-friendly — things can shift | Less concrete for stakeholders |
| Focuses on priority, not timeline | |

**Who uses this**: Consumer tech companies with no hard deadlines (Google, Facebook, Twitter).

## Key Takeaway

> Quarterly roadmaps are okay as a **general guide** — but tell everyone "this may change." The agile way is **Now / Next / Later**.

---

## Buzzwords

| Term | Definition |
|---|---|
| **Roadmap** | Plan of what gets built and roughly when |
| **Epic** | Grouping of features that takes >1 sprint to build |
| **Story Points** | Measure of difficulty (not time) assigned by engineers |
| **Velocity** | Average story points completed per sprint — used to predict future delivery |
| **Sprint Planning** | Meeting to scope work and estimate story points for next sprint |
| **Acceptance Criteria** | Specific testable conditions a feature must satisfy |
| **QA** | Quality Assurance — testing phase before release |
